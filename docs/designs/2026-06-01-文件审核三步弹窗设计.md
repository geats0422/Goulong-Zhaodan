# 文件审核三步弹窗设计

## 目标
为体检台补齐“上传文件 -> 解析确认 -> 配置知识库 -> 执行审查 -> 查看报告”的三步文件审核弹窗流程。审查场景不再由用户手动选择，而是在文件解析阶段识别为 `合同` 或 `招投标文件`，并驱动后续知识库召回与审查。

## 用户场景
用户在靶场大盘点击“发起智能初审”并选择文件后，系统打开文件审核弹窗。

Step 1 解析文件：系统上传并解析文件，展示与体检台列表一致的文件信息，包括文件名称、文件大小、文件格式、文件类型（合同/招投标文件）。解析完成后用户确认进入下一步。

Step 2 审查准备：弹窗变为左右布局。左侧为文档预览组件，右侧为知识库配置与审查按钮。用户可以启用/停用自己的知识库，系统默认知识库始终挂载。审查场景只读显示，由 Step 1 的文件类型识别结果决定，不提供下拉选择。

Step 3 审查报告：沿用当前体检台的最终报告体验，左侧展示文档，右侧展示智能审查诊断书。用户点击“导出体检报告”导出报告。

## 设计依据
遵循根目录 `DESIGN.md`：
- 风格：Neo-Chinese Cyberpunk，古典权威感与技术界面结合。
- 主色：Obsidian/Deep Charcoal 作为底色，Brushed Gold 作为主动作和焦点。
- 布局：12 栅格、强留白、纵向卷宗感。
- 卡片：1px 低透明金色/炭色边框，不依赖阴影。
- 标签：仅用于系统状态、风险状态、索引状态，不用于普通说明文本。
- 深浅主题：正文与元信息必须满足可读对比，浅色主题下正文使用深色，不使用低透明浅色文字。

## 推荐方案
采用“真实解析会话接口 + 前端三步弹窗”的方案。

不采用纯前端模拟流程，因为现有后端 `POST /inspection/upload` 是“上传 + 审查”一体接口，且仍依赖前端传入 `application_scenario`。纯前端模拟无法满足“审查场景由解析文件信息识别”的要求，也无法为知识库启停、文档预览、报告导出建立可靠的数据基础。

## 前端方案
### 新增组件
建议新增：

`frontend/src/components/inspection/InspectionReviewModal.vue`

职责：
- 管理三步状态：`parsing`、`prepare`、`report`。
- 展示 Step 组件与当前步骤内容。
- 持有解析会话、知识库启停、审查报告数据。
- 负责调用解析、知识库设置、执行审查、导出报告相关接口。

建议拆分子组件：
- `InspectionStepHeader.vue`：顶部步骤条。
- `InspectionFileSummary.vue`：Step 1 文件信息。
- `DocumentPreviewPane.vue`：Step 2/Step 3 左侧文档预览。
- `KnowledgeTogglePanel.vue`：Step 2 右侧知识库启停。
- `InspectionReportPane.vue`：Step 3 右侧审查诊断书，可复用 `InspectionDeskPage.vue` 现有报告结构。

如果实现初期希望更小改动，可先把子组件写在 `InspectionReviewModal.vue` 内，后续再拆分。

### Dashboard 接入
修改 `frontend/src/pages/DashboardPage.vue`：
- 文件选择后不再直接 `window.location.href = '/inspection-desk'`。
- 打开 `InspectionReviewModal` 并传入 `File` 对象。
- 弹窗完成审查后，可以保留在弹窗 Step 3，也可以提供“进入体检台详情”按钮跳转到 `/inspection-desk?record=<id>`。

### InspectionDesk 调整
修改 `frontend/src/pages/InspectionDeskPage.vue`：
- 移除顶部“审查场景”下拉选择。
- 改为只读展示：`审查场景：招投标文件` 或 `审查场景：合同`。
- 保留“导出体检报告”和“物理销毁案卷”。
- 当前静态报告布局可作为 Step 3 弹窗报告面板的视觉参考。

### Step 组件视觉设计
Step 条位于弹窗顶部：
- Step 1：解析文件
- Step 2：审查准备
- Step 3：审查报告

状态规则：
- 未开始：灰金线框、低透明文本。
- 当前：金色描边 + 细微 glow。
- 完成：金色实心小方点或 check 图标，避免 emoji。
- 错误：红色边框 + 错误提示文本。

### Step 1 内容
布局：居中窄卡片，强调“解析案卷”。

展示字段：
- 文件名称
- 文件大小
- 文件格式
- 文件类型：合同 / 招投标文件
- 页数或字符数（如果后端可提供）
- 解析状态：解析中 / 已完成 / 失败

文件类型显示为普通字段，不使用可编辑控件。

错误处理：
- 文件格式不支持：显示错误并允许重新选择。
- 文件过大：显示 20MB 限制。
- 文本过短：提示无法体检。
- 类型识别置信度不足：默认归为招投标文件，并显示“系统初判，可在后续版本支持人工修正”。当前版本不提供手动选择。

### Step 2 内容
左右布局：
- 左侧 `DocumentPreviewPane`：展示上传文件预览。
- 右侧 `KnowledgeTogglePanel`：展示审查准备项。

右侧内容：
- 文件类型：只读。
- 系统默认知识库：只读启用。
- 用户知识库：列表展示用户文档，可切换启用/停用。
- 违禁词来源：显示“已挂载用户配置违禁词”。
- 主按钮：开始审查。

知识库启停沿用设置页能力：
- 用户知识库可切换。
- 系统默认知识库不可关闭。
- 切换应即时保存或在“开始审查”前批量保存。推荐即时保存，避免步骤退出时状态丢失。

### Step 3 内容
左右布局复用体检台视觉：
- 左侧：文档预览，支持高亮命中片段。
- 右侧：智能审查诊断书。

右侧报告包含：
- 报告标题
- 风险摘要 chip
- 问题列表
- 每个问题包含位置、诊断对象、修复建议、引用标尺
- 审查结束分隔线

按钮：
- 导出体检报告
- 返回审查准备
- 关闭弹窗

## 后端方案
### 新增解析会话模型（内存 MVP）
初版可使用内存会话，后续再持久化到 PostgreSQL。

建议结构：

```python
InspectionSession = {
    "id": str,
    "user_id": int,
    "filename": str,
    "file_size": int,
    "file_format": str,
    "document_type": "bidding" | "contract",
    "document_type_label": "招投标文件" | "合同",
    "text": str,
    "text_preview": str,
    "created_at": str,
}
```

安全要求：
- 会话必须按 `user_id` 隔离。
- 审查接口根据 `session_id + current_user` 读取，不允许跨用户访问。
- 内存会话设置过期时间，避免长期占用内存。

### 新增接口：解析文件
`POST /inspection/parse`

表单：
- `file`: 上传文件

响应：

```json
{
  "session_id": "...",
  "file": {
    "name": "A区数据中心项目招标文件_v2.pdf",
    "size": 1048576,
    "format": "pdf",
    "document_type": "bidding",
    "document_type_label": "招投标文件",
    "text_preview": "..."
  }
}
```

文件类型识别规则 MVP：
- 文件名或正文包含 `合同`、`协议`、`甲方`、`乙方`、`民法典`、`违约责任`：倾向 `contract`。
- 文件名或正文包含 `招标`、`投标`、`招投标`、`采购`、`评标`、`中标`、`投标人`：倾向 `bidding`。
- 同时命中时按关键词权重判断。
- 无法判断时默认 `bidding`，并在响应中可附加 `confidence: "low"`。

### 新增接口：执行审查
`POST /inspection/sessions/{session_id}/inspect`

请求体：

```json
{
  "project_id": "default"
}
```

说明：
- 不再接收 `application_scenario`。
- 后端从解析会话读取 `document_type`，映射为现有 `application_scenario`。
- 调用 `retrieve_regulation_base(db, user_id, application_scenario, limit=8)`。
- 合并用户保存的违禁词。
- 调用 `run_inspection(text, deps)`。
- 生成 `_inspection_records` 记录。

响应可以复用现有 `InspectionReportResponse`，并扩展文件信息：

```json
{
  "id": 1,
  "overall_risk": "low",
  "summary": "...",
  "issues": [],
  "regulation_refs": [],
  "document_name": "...",
  "document_type": "bidding",
  "document_type_label": "招投标文件"
}
```

### 兼容策略
保留现有 `POST /inspection/upload` 一段时间，避免现有测试和调用直接失效。

迁移路径：
- 新 UI 使用 `/inspection/parse` + `/inspection/sessions/{session_id}/inspect`。
- 旧 `/inspection/upload` 可以继续支持 `application_scenario`，但前端不再使用。
- 后续稳定后再决定是否废弃旧接口。

## 数据流
1. 用户在 Dashboard 选择文件。
2. 前端打开 `InspectionReviewModal`。
3. Step 1 调用 `/inspection/parse`。
4. 后端读取文件、提取文本、识别文件类型、创建解析会话。
5. 前端展示文件信息。
6. 用户进入 Step 2。
7. 前端加载设置页知识库概览或复用现有设置 API，展示可启停的用户知识库。
8. 用户点击“开始审查”。
9. 前端调用 `/inspection/sessions/{session_id}/inspect`。
10. 后端按解析得到的文件类型召回默认知识库 + 用户启用知识库 + 违禁词，执行审查。
11. 前端进入 Step 3，展示报告。
12. 用户导出体检报告。

## 主题与可读性
深色主题：
- 弹窗背景：`#0a0a0a` / `#121212`。
- 主文字：`#e5e2e1`。
- 次级文字：`#d0c5af`，避免低于 70% 透明度。
- 主动作：`#f2ca50`。

浅色主题：
- 弹窗背景：`#fbf6ea` 或 `#ffffff`。
- 主文字：`#1f1a12`。
- 次级文字：`#5f5038`，不使用浅灰透明文本。
- 边框：`rgba(184, 146, 42, 0.35)`。
- 状态 chip 文字使用深棕/深红/深绿，确保肉眼可读。

## 错误处理
- 解析失败：停留 Step 1，展示失败原因和重新选择文件按钮。
- 会话过期：提示重新上传文件。
- 知识库加载失败：Step 2 显示重试按钮，但默认知识库说明仍展示。
- 审查失败：停留 Step 2 或进入错误态 Step 3，允许重试审查。
- 导出失败：报告页显示非阻塞错误提示。

## 测试策略
### 后端测试
- `/inspection/parse` 返回文件名称、大小、格式和识别出的文件类型。
- 合同关键词文件识别为 `contract`。
- 招投标关键词文件识别为 `bidding`。
- `/inspection/sessions/{session_id}/inspect` 不接收前端场景，使用会话中的文件类型召回知识库。
- 跨用户访问其他人的 `session_id` 返回 404 或 403。
- 过短文件、超大文件、不支持格式返回正确错误。

### 前端测试/验证
- Dashboard 选择文件后打开三步弹窗，不直接跳转。
- Step 1 展示文件名称、大小、格式、文件类型。
- Step 2 文件类型为只读，不出现审查场景下拉。
- Step 2 可展示并切换用户知识库。
- Step 3 展示左文档右审查书，导出按钮存在。
- 深浅主题下 Step 文案、文件信息、按钮、状态 chip 均清晰可读。

## 非目标
- 本次不实现真实 PDF 翻页渲染器，可先使用文本预览/模拟纸张视图。
- 本次不实现向量检索排序。
- 本次不实现历史记录持久化重构。
- 本次不移除旧 `/inspection/upload` 接口。
- 本次不允许用户手动修改审查场景。

## 开放问题
- 导出体检报告初版是否只导出 HTML/文本，还是需要 PDF？建议初版先导出 HTML 或 JSON，再迭代 PDF。
- 解析会话是否需要落库？建议 MVP 使用内存会话，待历史记录与报告详情页稳定后再持久化。
