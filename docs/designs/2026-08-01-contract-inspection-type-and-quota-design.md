# 合同初审类型与额度策略设计

## 目标

将照胆明确定位为“合同初审”智能体，修正 Step 2 将合同误显示为招投标文件的问题，并将工程类别、合同类别、知识库选择拆成清晰的独立维度。

同时规范本地与生产环境的额度策略，避免本地调试受额度拦截，并将额度不足入口统一指向设置页的账单订阅管理。

## 用户场景

1. 用户上传工程分包合同。
2. 系统完成文档解析，并识别合同的工程类别与合同类别，提供推荐值和置信度。
3. 用户在 Step 2 手动确认或修改两个类别。
4. 系统根据用户已启用的知识库提供审查依据；若没有用户启用文档，则回退到系统默认知识库。
5. 用户开始合同初审并查看报告。
6. 用户额度不足时，进入设置页的“账单与订阅管理”进行处理。

## 分类模型

工程类别与合同类别是两个独立维度，不得混用。

### 工程类别

- 房建施工
- 市政道路
- 装饰装修
- 机电安装
- 钢结构
- 通用工程

### 合同类别

- 劳务分包
- 专业工程分包
- 其他类

首期系统提供以上预设；用户可以新增、编辑、停用自己的私有类别。用户私有类别只对本人可见，不影响其他用户。

AI 采用“规则初筛 + 模型判断”：根据文件名、章节标题和正文关键词初筛，再由模型返回工程类别、合同类别、置信度和判断依据。AI 结果只作为推荐，最终以用户在 Step 2 的选择为准。

## Step 2 交互

Step 2 标题为“合同初审准备”，不再出现“招投标/合同”场景切换。

页面结构：

```text
合同大类：工程建设合同 · 合同初审

AI 推荐工程类别：市政道路       置信度：高
工程类别：[市政道路 ▼]

AI 推荐合同类别：专业工程分包   置信度：中
合同类别：[专业工程分包 ▼]

审查依据
用户知识库：用户已启用的相关文档
无用户启用文档时：系统默认知识库

[开始审查]
```

用户可以修改两个类别。中、低置信度时展示提醒，但不阻止用户在确认类别后开始审查；无法识别时使用“通用工程 + 其他类”作为推荐值。

## 知识库选择

知识库按用户配置优先级处理：

1. 查询当前用户在对应工程类别和合同类别下已启用的知识库文档。
2. 如果至少存在一份用户已启用文档，Step 2 只展示这些用户知识库文档。
3. 如果用户没有任何已启用文档，Step 2 展示系统默认知识库文档。
4. 用户已上传但停用的文档不参与本次审查，也不触发用户知识库优先级。

知识库文档需要支持工程类别和合同类别的绑定；无法精确绑定的文档可以作为通用合同规则参与回退检索。

### 招投标知识库收敛

照胆只做合同初审，知识库上传表单不再提供“招投标”应用场景，只保留合同场景。

已有招投标相关系统知识库采用停用和隐藏策略：

1. 不删除数据库记录、索引节点或文件存储，保留后续恢复能力。
2. 将招投标相关文档标记为停用，不参与合同初审检索。
3. 默认知识库概览、知识库管理页、Step 2 审查依据面板均不展示停用的招投标文档。
4. 上传知识库时固定写入合同场景，不再提交 `application_scenario=bidding`。
5. 旧记录中引用过招投标知识库的历史报告保持可查看，但重审时不再使用已停用文档。

系统默认合同规则包首期从官方公开来源整理，包含：

- 《中华人民共和国民法典》第三编合同
- 《中华人民共和国建筑法》
- 《建设工程质量管理条例》
- 《建设工程安全生产管理条例》
- 《中华人民共和国安全生产法》
- 《保障农民工工资支付条例》
- 建设工程施工合同纠纷相关司法解释
- 官方建设工程施工合同示范文本中与合同条款相关的部分

法规文件通过官方域名白名单整理，导入前人工审核，并保存官方 URL、发布日期、施行日期、版本说明、抓取日期和哈希。法规不直接作为二进制文件提交 Git，使用 manifest 与管理员导入脚本维护。新版本导入后旧版本停用但不删除。

首期所有工程类别共享“通用工程合同规则包”；房建、市政、装修等专项规则包后续再增加。

知识库上传表单统一使用工程类别和合同类别，不再使用“新基建/传统基建/城市更新”旧分类。新上传固定为合同场景，不接受 `application_scenario=bidding`。

用户上传的招投标知识库也归档隐藏，不参与合同初审但保留文件和历史记录。设置页提供“已归档招投标资料”只读区域，用户可以永久删除自己拥有的归档资料；删除时清理原文件、Markdown、索引节点、版本记录和知识库记录，并写审计日志。系统归档资料仅管理员或迁移脚本可清理。

用户知识库默认按工程类别和合同类别匹配并全选，用户可在 Step 2 多选本次审查依据。无任何匹配的用户已启用文档时，回退系统默认规则包；系统默认文档不与用户文档混合展示。

## 数据模型

新增工程类别/合同类别预设实体，至少包含：

- `id`
- `key`
- `name`
- `dimension`：`engineering` 或 `contract`
- `owner_type`：`system` 或 `user`
- `owner_user_id`
- `enabled`
- `created_at`
- `updated_at`

体检记录增加：

- `detected_engineering_type`
- `final_engineering_type`
- `detected_contract_type`
- `final_contract_type`
- `classification_confidence`
- `rule_package_key`
- `classification_source`
- `engineering_type_snapshot`
- `contract_type_snapshot`
- `knowledge_sources_snapshot`

知识库文档增加可选绑定字段：

- `engineering_type_key`
- `contract_type_key`

旧记录中的 `bidding` / `contract` 字段继续保留并可读。旧合同记录回填为“通用工程/其他类”，并标记 `classification_source=legacy`；旧招投标记录不重分类，标记为 `archived_legacy`，重审时提示场景已停用。旧记录没有新分类信息时展示“历史记录 / 通用工程合同”，不强制重跑。

系统类别使用稳定 slug；用户类别使用用户作用域 key。同一用户、同一维度下名称不允许重复。已被引用的类别不能删除，只能停用；历史记录保存当时的类别名称快照。

## 接口设计

```text
GET  /inspection/contract-types
POST /inspection/contract-types
PATCH /inspection/contract-types/{id}
DELETE /inspection/contract-types/{id}

GET  /inspection/engineering-types
POST /inspection/engineering-types
PATCH /inspection/engineering-types/{id}
DELETE /inspection/engineering-types/{id}

GET  /inspection/archived-knowledge
DELETE /inspection/archived-knowledge/{id}
```

解析任务完成后返回分类推荐信息。Step 2 提交最终选择：

```json
{
  "engineering_type_key": "municipal-road",
  "contract_type_key": "professional-subcontract",
  "knowledge_document_ids": [12, 18]
}
```

服务端必须校验类别 key、用户私有类别归属和知识库文档启用状态，不能直接信任模型返回值或前端提交值。

`application_scenario` 作为历史兼容字段保留，但新上传、新体检和新知识库接口不再接受 `bidding`。旧请求返回明确的 `deprecated_application_scenario` 错误；历史报告仍可查看，旧招投标记录不可按旧场景重审。

分类由独立合同分类器执行。分类器输入解析正文、文件名和规则初筛结果，输出严格结构化的工程类别、合同类别、置信度和证据。分类服务超时不阻塞 Step 2，使用“通用工程 + 其他类”并允许用户手动确认。production 中分类调用计入额度，local/development 只记录使用量不拦截。

## 额度策略

使用 `ENVIRONMENT` 明确控制额度行为：

- `local`：本地调试，不拦截额度。
- `development`：兼容旧配置，按 `local` 处理，并输出迁移提示。
- `production`：执行真实额度检查和额度消耗记录。
- 其他值：配置校验失败，禁止静默按本地模式运行。

本地环境可以记录计算消耗，便于观察调用量，但不因额度不足阻断请求。生产环境沿用 Membership 配额校验。

额度不足弹窗统一为：

```text
当前账户额度不足
本次审查需要更多算力额度。

[前往账单与订阅] [关闭]
```

按钮统一跳转 `/settings?tab=billing`，设置页读取 query 参数后自动打开“账单与订阅管理”Tab，不再默认跳转定价页。

风险报告增加一致性校验：`overall_risk` 只允许 `low/medium/high/critical`；若问题最高严重等级、摘要与模型标签冲突，服务端按问题最高严重等级提升风险，不降低风险。UI、历史列表和 PDF 使用服务端最终风险等级。

## 错误处理

- 分类模型返回未知 key：降级为通用工程/其他类，并记录日志。
- 分类服务超时：保留规则初筛结果，要求用户确认后继续。
- 用户提交停用或无权限知识库文档：服务端拒绝并提示重新选择。
- 没有用户启用知识库：明确提示正在使用系统默认知识库。
- 生产环境配置为未知 `ENVIRONMENT`：启动配置校验失败。
- 旧记录无分类信息：详情页使用历史兼容展示，不影响查看报告。
- 系统或用户归档资料不得被普通用户重新启用为合同规则。

## 测试策略

### 后端

- 合同正文不会再被默认识别为招投标文件。
- 工程类别和合同类别可以独立保存、读取和修改。
- 模型未知 key、低置信度、超时均有降级行为。
- 用户私有类别隔离正确。
- 用户已启用知识库优先；无启用文档时回退系统默认。
- `local` / `development` 不拦截额度，`production` 拦截额度。
- 未知环境值启动失败。
- 额度不足响应包含设置账单入口所需错误码。
- 法规版本切换不改变历史报告的知识库版本快照。

### 前端

- Step 2 不再渲染招投标/合同切换。
- 工程类别和合同类别均可选择和修改。
- 低置信度提示正确显示。
- 用户知识库和系统默认知识库回退状态正确展示。
- 额度弹窗跳转 `/settings?tab=billing` 并打开对应 Tab。
- 历史详情正确展示最终类别、识别置信度和知识库来源。
- 已归档招投标资料只读展示和用户完整删除流程正确。
- HelpPage、DeveloperDocs、README/API 文档不再把招投标作为新业务入口。

## 实施边界

这是跨前后端、数据库、知识库检索、法规导入和模型分类的结构性改动，需要新增 Alembic 迁移和幂等存量回填，不修改历史迁移文件。实现前应先拆分实施计划，不直接在现有 `bidding/contract` 场景字段上继续堆叠临时分支。
